A binding gives a name to a value. It owns its data, has one type, and stays alive until it goes out of scope.

## Bindings

`let` creates a mutable binding, `const` creates one that cannot change after initialization:

```zn
fn main() {
  let count = 0;
  count += 1;

  const limit = 100;

  @println("{} {}", count, limit);
}
```

An explicit type annotation is optional:

```zn
fn main() {
  let full: i32 = 123;
  let short = 123;

  @println("{} {}", full, short);
}
```

A binding can start without a value, but it must be assigned before it is read:

```zn
fn main() {
  let answer: i32;

  answer = 42;

  @println("{}", answer);
}
```

Reading it earlier is `zeen::dataflow::use_of_uninitialized`, one of the checks behind [Compiler Errors](/getting-started/compiler-errors/).

## Type inference

The compiler infers a binding's type from how the binding is used later. The type is chosen once and applies to every use, and inference never converts a value: `let value = 1; let byte: u8 = value;` makes `value` a `u8`, it does not copy an `i32` into a `u8`.

:::caution[The binding type is fixed by later use]
The type of a binding can be decided by a line that comes after it, and that type then holds for the whole function. Rust and C fix the type at the declaration, so this is the first habit to unlearn.

```zn
fn main() {
  let value = 1;
  let byte: u8 = value;

  @println("{} {}", @typename(typeof value), @typename(typeof byte));
}
```

```text
u8 u8
```

`value` is a `u8` everywhere in `main`, including any line that comes before the annotation. Adding a second consumer with a different type is a compile error, not a conversion:

```zn
fn main() {
  let value = 1;
  let byte: u8 = value;
  let size: usize = value;
}
```

```text
zeen::typechecker::ambiguous_inference

  × conflicting inferred types for `value`: `u8` and `usize`
  help: annotate `value` with an explicit type
```

Write `let value: usize = 1;` when two consumers disagree.
:::

A hint can come from anywhere the value meets a known type:

| Hint | Example |
|---|---|
| annotation on another binding | `let value = 1; let byte: u8 = value;` |
| argument of a function call | `take(n)`, where `take` takes a `u8` |
| `return` from a function with a known return type | `fn small() u8 { let n = 1; return n; }` |
| operand of an arithmetic or comparison expression | `let wide = 1; let wide_value: i64 = wide + 2;` |
| element of an annotated array | `let bytes = {1, 2}; let packed: [2]u8 = bytes;` |
| branch of `if` or `switch` | `let result = if (flag) 1 else 2; let byte: u8 = result;` |
| later assignment | `let x; x = 5;` |

An element of an annotated array sets the type of the whole literal:

```zn
fn main() {
  let bytes = {1, 2};
  let packed: [2]u8 = bytes;

  @println("{} {}", packed[0], packed[1]);
}
```

Inference works through `@uninit()` as well. It produces a value of the annotated type without writing it, so a function can fill an array field by field:

```zn
fn fill(source: []const u8) [3]u8 {
  let copy: [3]u8 = @uninit();

  copy[0] = source[0];
  copy[1] = source[1];
  copy[2] = source[2];

  return copy;
}

fn main() {
  const source: [3]u8 = {1, 2, 3};
  const copy = fill(source[..]);

  @println("{}", copy[0]);
}
```

Reading the value before it is written is undefined behavior. [Builtin Macros](/language-basics/macros-builtin/) covers `@uninit` and the rest of the macros.

Without a hint a literal keeps its default type: `i32` for an integer, `f64` for a float.

```zn
fn main() {
  let count = 1;
  let ratio = 1.5;

  @println("{} {}", @typename(typeof count), @typename(typeof ratio));
}
```

An explicit annotation wins over every hint, and there is no implicit widening between integer types, so later uses cannot widen or narrow it:

```zn
fn main() {
  let value: u8 = 1;
  let size: usize = value;
}
```

The second line is `zeen::typechecker::mismatch`. A literal inferred into a narrow type is still range checked: `let n = 300; let byte: u8 = n;` reports `zeen::typechecker::int_literal_out_of_range` at the literal.

Inference has limits: a struct field, an enum payload, an index expression and an array to pointer conversion do not feed a hint back into a binding, and globals always need an explicit type.

## Globals

Top-level globals need both an explicit type and an initializer:

```zn
const MAX: i32 = 100;
let counter: i32 = 0;

fn main() {
  @println("{} {}", MAX, counter);
}
```

A global can hold a function value: a named function or an `fn` literal.

```zn
fn double(x: i32) i32 {
  return x * 2;
}

let handler: fn(i32) i32 = double;
let triple: fn(i32) i32 = |x| x * 3;

fn main() {
  @println("{} {}", handler(2), triple(2));
}
```

Globals are initialized before `main` runs. Mutable globals are checked for cycles between their initializers and report `zeen::resolver::global_var_cycle` when two depend on each other.

## Discard

`let _ = value;` discards the value without binding it. Nothing is dropped, so a `Drop` value discarded this way leaks:

```zn
fn main() {
  let _ = String.from("not dropped");
}
```

`String` is the heap string from [std.string](/library/std/string/), and its buffer belongs to the value. [Move Semantics](/ownership-types/move-semantics/) explains `Drop`.

Name the binding when the value must be released at the end of the scope:

```zn
fn main() {
  let _held = String.from("dropped at scope end");

  @println("done");
}
```

The leading underscore only silences the unused warning. `_held` still drops at the end of the scope, while a bare `_` drops nothing.

## Memory model

A local binding lives in the stack frame of the current function, and the heap data it owns is released when the binding is dropped. The frame goes away when the function returns.

```zn
fn main() {
  let a = 1234;
  let ptr = &a;

  @println("{}", *ptr);
}
```

The frame holds both values, and `ptr` holds the address of `a`:

```text
stack frame of main
┌──────────┬───────────────┐
│ binding  │ value         │
├──────────┼───────────────┤
│ ptr      │ address of a  │──┐
├──────────┼───────────────┤  │
│ a        │ 1234          │◄─┘
└──────────┴───────────────┘
```

Pointers are values too and live in the same frame. [Pointers](/language-basics/pointers/) covers them in detail.
