**Zora** builds projects, resolves git dependencies and runs the test suite. It ships as the `zora` binary in each release and needs no network setup beyond git.

## Project layout

<FileTree>
  - my-project
    - Zora.toml project manifest
    - Zora.lock resolved dependencies
    - .gitignore
    - src
      - main.zn entry point (`bin`), or index.zn (`lib/*`)
    - dist/ build output
</FileTree>

## Quick start

```bash
zora new hello
cd hello
zora run
```

`zora new` writes the manifest, a `Zora.lock` and a `src/main.zn` that prints a line. `zora init` does the same in the directory you are already in. Both take `--lib` to create a library package instead of a binary.

## Commands

| Command | Flags | Description |
|---------|-------|-------------|
| `zora init` | `--lib` | Initialize a project in the current directory |
| `zora new <name>` | `--lib` | Create a new project directory |
| `zora build` | `-m --mode [Debug/Release]`, `--release`, `--debug`, `--target <TRIPLE>`, `--emit <EMIT>` | Build the project |
| `zora run` | `-m --mode [Debug/Release]`, `--release`, `--debug`, `[-- <ARGS>...]` | Build and run the project |
| `zora test` | | Run the project's test suite |
| `zora add <git-url>` | `--branch <BRANCH>` | Add a dependency |
| `zora remove <name>` | | Remove a dependency |
| `zora update` | | Update lockfile dependencies from the manifest |
| `zora check` | `--all` | Check the project config and source, `--all` walks every module |
| `zora clean` | `--global` | Remove build artifacts and caches |
| `zora deps-map` | | Print the dependency sources map |

Two flags work on every subcommand: `--no-color` and `--manifest-path <PATH>`, which points at a `Zora.toml` outside the current directory and defaults to searching the parent directories.

## Manifest

```toml
[package]
name = "hello"
version = "0.0.0"
zeen = "^0.6.0"
type = "bin"
description = "A small Zeen program"

[build]
output = "hello"
flags = ["--no-warns"]
link = ["raylib"]

[build.os.linux]
link = ["raylib", "m", "pthread", "dl", "rt", "GL", "X11"]

[build.os.windows]
link = ["raylib", "winmm", "gdi32", "opengl32", "shell32", "ole32"]

[dependencies]
greeting = "https://github.com/mealet/greeting"
math = { git = "https://github.com/mealet/math", rev = "dev" }
```

### `[package]`

| Field | Description |
|-------|-------------|
| `name` | Package name, also the default output name |
| `version` | Package version |
| `zeen` | Required compiler version |
| `type` | `bin`, `lib/static` or `lib/dynamic` |
| `description` | Optional package description |
| `authors` | Optional author list |
| `repository` | Optional repository URL |
| `license` | Optional license identifier |

Both version fields follow semver: `1.4.2` is major, minor and patch, and a caret range such as `^0.6.0` accepts any `0.6.x` release but not `0.7.0`. Zora compares `zeen` against `zeen --version` before the build and stops when the installed compiler falls outside the range.

### `[build]`

| Field | Description |
|-------|-------------|
| `output` | Output name, overriding the package name |
| `flags` | Extra flags passed to the compiler |
| `link` | Native libraries to link, repeated as `--link` |
| `link-dir` | Native library search directories, relative to the package root, repeated as `--link-dir` |

### `[dependencies]`

Each entry maps a package name to a git source: a bare URL or a `{ git, rev }` pair. `rev` may be a commit, tag or branch. Dependencies are resolved into `Zora.lock`, which pins every one to a commit.

```toml
[dependencies]
sample = "https://..."
another = { git = "https://...", rev = "12345678" }
```

### Platform sections

A `[build.<selector>.<value>]` sub-table overrides `[build]` on one platform. Selector values use the same vocabulary as [conditional compilation](/language-basics/conditional-compilation/) (`@os`, `@arch`, `@env`, `@family`, `@target`).

| Section | Example |
|---|---|
| `build.target` | `[build.target.x86_64-unknown-linux-gnu]` |
| `build.arch` | `[build.arch.aarch64]` |
| `build.env` | `[build.env.musl]` |
| `build.os` | `[build.os.linux]` |
| `build.family` | `[build.family.unix]` |

The override takes the same fields as `[build]`: `output`, `flags`, `link`, `link-dir`. First match wins, in this order: `target`, `arch`, `env`, `os`, `family`.

An override replaces `[build]` whole, with no merge, so repeat every field the platform needs. The manifest example repeats `raylib` on purpose: leaving it out of the `linux` or `windows` table drops the library.

### Native dependencies

Link directives are collected through the whole dependency tree into `Zora.lock` and passed to the compiler on every build.

| Case | Handling |
|---|---|
| Library declares `link` | consumers link it automatically, no `[build]` section needed |
| Relative `link-dir` in a dependency | resolves against that dependency's checkout |
| Lockfile | records the build spec, platform sections included; re-resolves after a manifest or compiler version change |

## Build output

```bash
zora build --release
```

| Mode | Output dir |
|------|------------|
| `Debug` | `dist/debug/<name>` |
| `Release` | `dist/release/<name>` |

```bash
zora build --release
```

Builds are cached: unchanged inputs skip the compiler and print `<path> (cached)`. `ZORA_HOME` moves the global cache and database from `~/.zora`, and is read by `zora add`, `zora update` and `zora clean --global`.

### Libraries

| Library type | Output file |
|--------------|-------------|
| `lib/static` | `libNAME.a`, `NAME.lib` (MSVC) |
| `lib/dynamic` | `libNAME.so`, `NAME.dll` (Windows), `libNAME.dylib` (macOS) |

## Testing

Test files live in `tests/`, and two doc-comment attributes mark the tests inside:

| Attribute | Effect |
|---|---|
| `/// @test` | the function below is a test, and it must be `pub` |
| `/// @should-fail` | inverts the result, so a panic or a failed assertion passes |

Zora reads the source as text and looks for those exact lines. The compiler sees ordinary doc comments and ignores them.

```zn
use std.testing;

fn add_2(x: i32) i32 {
  x + 2
}

/// @test
pub fn add_test() {
  assert_eq(add_2(2), 4);
}

/// @test
/// @should-fail
pub fn fail_test() {
  assert_eq(add_2(2), 6);
}
```

`assert_eq` and the other assertions come from `std.testing`.

```bash
zora test
```

```text
Tests from `tests/add.zn`:
  test add.add_test ... [OK]
  test add.fail_test ... [OK]

Tests 2 passed in 0.06s
```

Each test builds as its own binary with the package root on the include path, so a test imports project code by its package name:

```zn
use std.testing;
use calc.math;

/// @test
pub fn triple_test() {
  assert_eq(triple(2), 6);
}
```

`zora test` runs every file under `tests/` and cannot pick one, so comment tests out while iterating. A compile error prints per test, with the compiler output under the failing line. `--manifest-path` points at another project.
