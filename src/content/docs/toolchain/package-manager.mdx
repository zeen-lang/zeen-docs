**Zora** builds projects, resolves git dependencies and runs the test suite. It ships as the `zora` binary in each release and needs no network setup beyond git.

## Project layout

<FileTree>
  - my-project
    - Zora.toml project manifest
    - Zora.lock resolved dependencies
    - .gitignore
    - src
      - main.zn entry point (`bin`), or index.zn (`lib/*`)
    - dist/ build output
</FileTree>

## Quick start

```bash
zora new hello
cd hello
zora run
```

`zora new` writes the manifest, a `Zora.lock` and a `src/main.zn` that prints a line. `zora init` does the same in the directory you are already in. Both take `--lib` to create a library package instead of a binary.

## Commands

| Command | Flags | Description |
|---------|-------|-------------|
| `zora init` | `--lib` | Initialize a project in the current directory |
| `zora new <name>` | `--lib` | Create a new project directory |
| `zora build` | `-m --mode [Debug/Release]`, `--release`, `--debug`, `--target <TRIPLE>`, `--emit <EMIT>` | Build the project |
| `zora run` | `-m --mode [Debug/Release]`, `--release`, `--debug`, `[-- <ARGS>...]` | Build and run the project |
| `zora test` | | Run the project's test suite |
| `zora add <git-url>` | `--branch <BRANCH>` | Add a dependency |
| `zora remove <name>` | | Remove a dependency |
| `zora update` | | Update lockfile dependencies from the manifest |
| `zora check` | `--all` | Check the project config and source, `--all` walks every module |
| `zora clean` | `--global` | Remove build artifacts and caches |
| `zora deps-map` | | Print the dependency sources map |

Two flags work on every subcommand: `--no-color` and `--manifest-path <PATH>`, which points at a `Zora.toml` outside the current directory and defaults to searching the parent directories.

## Manifest

```toml
[package]
name = "hello"
version = "0.0.0"
zeen = "^0.6.0"
type = "bin"
description = "A small Zeen program"

[build]
output = "hello"
flags = ["--no-warns"]
link = ["raylib"]

[build.os.linux]
link = ["raylib", "m", "pthread", "dl", "rt", "GL", "X11"]

[build.os.windows]
link = ["raylib", "winmm", "gdi32", "opengl32", "shell32", "ole32"]

[dependencies]
greeting = "https://github.com/mealet/greeting"
math = { git = "https://github.com/mealet/math", rev = "dev" }
```

### `[package]`

| Field | Description |
|-------|-------------|
| `name` | Package name, also the default output name |
| `version` | Package version |
| `zeen` | Required compiler version |
| `type` | `bin`, `lib/static` or `lib/dynamic` |
| `description` | Optional package description |
| `authors` | Optional author list |
| `repository` | Optional repository URL |
| `license` | Optional license identifier |

Both version fields follow semver: `1.4.2` is major, minor and patch, and a caret range such as `^0.6.0` accepts any `0.6.x` release but not `0.7.0`. Zora compares `zeen` against `zeen --version` before the build and stops when the installed compiler falls outside the range.

### `[build]`

| Field | Description |
|-------|-------------|
| `output` | Output name, overriding the package name |
| `flags` | Extra flags passed to the compiler |
| `link` | Native libraries to link, repeated as `--link` |
| `link-dir` | Native library search directories, relative to the package root, repeated as `--link-dir` |

### `[dependencies]`

Each entry maps a package name to a git source: a bare URL or a `{ git, rev }` pair. `rev` may be a commit, tag or branch. Dependencies are resolved into `Zora.lock`, which pins every one to a commit.

### Platform sections

`[build]` accepts per-platform sub-tables. Selector values use the same vocabulary as the compiler directives (`@os`, `@arch`, `@env`, `@family`, `@target`):

- `[build.target.<triple>]`
- `[build.arch.<value>]`
- `[build.env.<value>]`
- `[build.os.<value>]`
- `[build.family.<value>]`

An override carries the same fields as `[build]`: `output`, `flags`, `link`, `link-dir`.

The override replaces the base `[build]` entirely, there is no merge. Repeat every field the platform needs, `link` included.

Precedence, first match wins: `target`, `arch`, `env`, `os`, `family`.

The example above links `raylib` twice on purpose: the base table carries it, and each platform override repeats it together with the platform libraries. A missing repeat would drop it, since Linux and Windows override sections replace the base table.

### Native dependencies

Link directives from the package and its dependencies, transitively, are collected into `Zora.lock` and passed to the compiler at build time.

A consumer of a library that declares `link` (for example `zora add .../zaylib`) links it automatically, with no `[build]` section in the consumer manifest.

A relative `link-dir` inside a dependency resolves against that dependency checkout.

The lockfile records the build spec, platform sections included. When the manifest or the compiler version changes, the next `zora build` or `zora check` re-resolves it.

## Dependencies

```bash
zora add https://github.com/mealet/greeting
zora add https://github.com/mealet/math --branch dev
zora remove math
zora update
```

Resolved dependencies reach the compiler as `--pkg` arguments, with the package name mapped to its `src` directory:

```bash
zeen src/main.zn out --pkg greeting=/home/you/.zora/git/checkouts/1a2b3c/9f8e7d/src
```

After that, `use greeting;` works anywhere the compiler looks, and a module inside the package is `use greeting.<module>;`. `zora deps-map` prints the same mapping without building:

```text
greeting=/home/you/.zora/git/checkouts/1a2b3c/9f8e7d/src
math=/home/you/.zora/git/checkouts/44ff01/0ac9be/src
```

The project itself is passed to the compiler the same way, under its `[package] name`. A project without dependencies prints nothing.

## Build output

```bash
zora build --release
```

| Mode | Output dir |
|------|------------|
| `Debug` | `dist/debug/<name>` |
| `Release` | `dist/release/<name>` |

Passing `--target` adds the triple, `dist/<triple>/<mode>/<name>`, with a `.exe` suffix on Windows.

Builds are cached: when the inputs did not change, `zora build` skips the compiler and prints `<path> (cached)`.

`ZORA_HOME` overrides the global cache and database directory, default `~/.zora`. It is used by `zora add`, `zora update` and `zora clean --global`.

### Libraries

| Library type | Output file |
|--------------|-------------|
| `lib/static` | `libNAME.a`, `NAME.lib` (MSVC) |
| `lib/dynamic` | `libNAME.so`, `NAME.dll` (Windows), `libNAME.dylib` (macOS) |

## Testing

Test files live in `tests/`. Zora scans each file for two attributes, written as doc comments:

```zn
use std.testing;

fn add_2(x: i32) i32 {
  x + 2
}

/// @test
pub fn add_test() {
  assert_eq(add_2(2), 4);
}

/// @test
/// @should-fail
pub fn fail_test() {
  assert_eq(add_2(2), 6);
}
```

`/// @test` marks the function that follows it as a test. The marker has to be a doc comment because it sits in ordinary Zeen source and the compiler ignores it, while Zora reads the file as text and finds the exact line. The function must be `pub`, or Zora stops with an error naming the file and line.

`/// @should-fail` inverts the result: the test passes when the program exits with a non-zero code, which is what a panic or a failed `assert_eq` produces. It is the way to test that a panic happens, or that an error path is reached.

`assert_eq` and the other assertions come from `std.testing`.

```bash
zora test
```

```text
Tests from `tests/add.zn`:
  test add.add_test ... [OK]
  test add.fail_test ... [OK]

Tests 2 passed in 0.06s
```

Each test compiles into its own binary, with the package root on the include path, so a test file imports project code by package name:

```zn
use std.testing;
use calc.math;

/// @test
pub fn triple_test() {
  assert_eq(triple(2), 6);
}
```

A single file cannot be selected: `zora test` runs every test in every file under `tests/`. Use `--manifest-path` to point at another project, or comment out tests while iterating. Compile errors are reported per test, with the compiler output under the failing line.
